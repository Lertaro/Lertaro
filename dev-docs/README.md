# dev-docs

Lertaro 的开发文档。这里不放使用说明（那些在 `Site/` 的用户指南里），只放**接手这个仓库的人需要的机制、决策与踩坑记录**：
某件事为什么这么实现、走过哪些不通的路、量到的数字是多少、还没收口的是什么。

先读 `pitfalls.md`。它是入口文档，收的是可跨主题复用的判断（怎么验证、怎么决策、构建与测试的坑、Windows 与 .NET
环境事实、反复要用的机制事实）。每篇主题文档只讲自己那个主题，细节不重复。

## 命名与写法约定

- 文件名全小写英文 kebab-case，名字说明主题，不带日期、大写前缀或个人代号。
- 一个主题只留一篇权威文档。新的调查结论并进对应主题文档；没有对应主题文档时，先判断它是不是 `pitfalls.md`
  里的一条经验。
- 每篇开头一行写清适用范围与核对基线（哪个分支、哪个提交），正文里的"现状/待办"以此为准。分支推进后如果没重核，
  就地标"未核对（截至 <commit>）"，不要删也不要凭印象改写。
- 过时内容处理：被后续提交替换或否证的判断，删掉取证过程，在"坑/教训"类小节留一行结论（为什么不通、别再走这条路）。
  数字被新量测推翻时，两个都留着。
- 代码位置写成 `文件.cs:行号` 或 `文件.xaml:行号`，提交只给 hash。行号随分支变动，核对不上就退化成文件与符号名。
- 不写只有作者本机才有的东西：绝对路径、用户名、一次性探针目录。命令和数字留着，路径用 `<repo>`、
  `%LOCALAPPDATA%` 这类通用写法。
- 面向的读者是人，不是某个模型的上下文：不写"我这次会话"式的过程记录，保留的是一审就能用的判断。

## 维护

- 本目录随仓库入库。重写大段前先用 `git log -- <文件>` 看清这段是什么时候、为解决什么写下的。
- 代码树与这里冲突时以代码为准，改这里；主题级深挖写进对应主题文档，并在上面的表里登记。
