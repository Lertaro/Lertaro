# 排序打分模型：从硬档位到可校准的分值

## 适用范围与核对基线

- 基线：`main` = `fd490885`（2026-10-21 核对）。排序相关代码最后改动 `8c754217`；现行行为以 `search-ranking.md` 为准。
- 本文是**历史方案**，不实施、不改代码。它与当时并行的 `search-ranking-redesign.md` 的重叠部分已经由现行 V2 取舍；下一轮工作只按 `search-ranking-intuition-plan.md` 分步执行，不能再从本文挑 P3/引擎键等步骤单独落地。
- 范围：快速窗口与完整窗口共用的评分内核、引擎截断键、参数校准与评测方法。内联窗口只在 §7.5 提一句。
- 目标：把用户给出的 6 档顺序写成**可推导、可校准、能在引擎侧执行**的整数分值，并让性能不低于现行实现。
- 非目标：不上线学习排序、不做云端个性化、不改索引格式、不为排序重建索引。

术语：

- **优先档**：索引规则里的高 / 正常 / 低（`IndexRuleEffect`）。
- **显示优先级**：设置 → 通用 → 快速搜索窗口 → 结果类型优先级（`UserSettings.ResultTypeOrder`）。
- **强匹配**：查询在文件名里落在词边界或词内连续段，且不是生僻读音；定义见 §3.2。
- **交换率**：一个匹配等级相当于几个优先档。0.8 表示“1 个匹配等级 ≈ 0.8 个优先档”。

## 0. 结论速览

1. 用户的 6 档顺序可以写成一个整数分 `S = 10·C + 8·P`：`C` 是强匹配（1/0），`P` 是高/正常/低（2/1/0）。四个非低档正好是 26 / 18 / 16 / 8，档 2（18）严格高于档 3（16），这就是 0.8 交换率的来源。
2. 分值不够，外面还要三层**硬门**（§3.1）：历史 ≥5 次、收藏、低优先。门是“成员资格”，不是偏好强度，所以不折算成分数；门内才用分值。低档门必须有（否则低档强匹配 10 压过正常弱匹配 8），历史和收藏门是产品置顶。
3. 真正的性能问题不在 App 的排序常数，而在“只要存在任意高档规则”就把请求抬到 1000：管道 4000 → 每盘扫描 160000，外加每个高档根一次独立补搜（每根 50 → 每盘 8000）。把分值编进引擎截断键后，可以回到 51/204/8160（每盘扫描量降到 1/19.6），并删掉补搜。
4. 科学性上，0.8 不是拟合出来的，而是一个**先验边际替代率**。加性形式在这里没有外推风险（特征只有 2×3 个离散格子，等价于查表），真正的假设是交换率恒定；理论边界见 §4.5，校准要靠 nDCG@10 与打开行为。
5. 历史次数是内生的（position bias）：排得越前越容易被打开，裸次数会自激。必须做时间衰减、条数上限、按查询条件化，并把 5/3 的阈值解释成“衰减后的等效次数”。
6. 类型顺序（显示优先级）在桶内压过匹配质量，是用户显式选择的硬约束，代价必须写进设置文案；低档是唯一例外，质量在前、类型在后。

## 1. 现行算法拆解

### 1.1 三条排序路径

| 路径 | 键序 | 位置 |
| --- | --- | --- |
| 快速窗口 | 优先档 → 类型 → 六质量键 → 收藏 → 历史 band → 历史 priority → 文件/目录 → 名序 → 长度 → 盘 → 路径 | `App/ViewModels/Search/Mapping/RankedCandidateOrdering.cs:54-66` |
| 完整窗口 | 优先档 → `RankSortKey>>32`（六质量键）→ 收藏 → 历史 band → 历史 priority → 文件/目录 → 名序 → 长度 → 盘 → 路径 → 低 32 位 | `Core/SearchResult.cs:104-132` |
| 引擎截断 | 只看质量键与引擎自身的 fzf tie-breaker，不看档位、历史、收藏 | `Core/Indexer/Usn/SearchCoordinator.cs:68` |

质量键的唯一顺序由 `MatchRank.CompareQuality` 定义（`Core/SearchIndex/MatchRank.cs:75`）：contiguity → shape → 左端连续 → start → coverage → tier。完整窗口把同一顺序打包成 `HighKey`（`Core/IndexV2/Search/SearchResultRelevance.cs:44-53`）。

档位由 `ExclusionRuleSet.GetPriority` 解析（路径规则按最近一层显式规则覆盖，模式规则沿链取最强），`SearchResultRankComparer.PriorityRank` 把它映射成 High=0 / Normal=1 / Low=2（`Core/SearchResult.cs:58-64`）。历史 band 只看裸次数：≥5 为 0，1–4 为 1，无历史为 2（`:77-80`）。

### 1.2 截断发生在排序之前

这是现行设计的结构性缺陷，也是“设了高档却看不到”的根源。

```text
App 请求 fileLimit
  → SearchService 对有限额乘 4（Core/Services/Search/SearchService.cs:48-51）
  → 每块盘的 NameSearch：keep = min(max(L,8)*8, 全部)，模式查询再扫 keep*5
  → FzfTopN 只留质量键最好的 keep 条，RefineRanks 再重排
  → 发出 L 条 → App 才拿到档位/历史
```

数字（`dev-docs/search-ranking.md` 的「候选预算与显示截断」已核对）：

| 场景 | App 限额 | 管道限额 | 每盘保留 | 每盘扫描 |
| --- | --- | --- | --- | --- |
| 普通查询 | 51 | 204 | 1632 | 8160 |
| 带 token / 文件夹范围 / filename-like / **有任意高档规则** | 1000 | 4000 | 32000 | 160000 |
| 每个高档根补搜 | 50 | 200 | 1600 | 8000 |

高档规则一旦存在，默认查询的每盘扫描量涨 19.6 倍；补搜再叠加 N 条完整管线（`App/ViewModels/Search/SearchStreamRenderer.cs:35,224-227`，`App/ViewModels/Search/ScopedSearchRunner.cs:52-63`）。补搜的注释自己写明这是为截断打的补丁：`ScopedSearchRunner.cs:46-51`。

完整窗口是另一个极端：`fileLimit = int.MaxValue`，`keep` 退化成“全部”，每个盘把整个索引扫一遍。此前实测（本机，2026-10-19）：`readme` 6.5 s / 23 MB，`read` 11.4 s / 66 MB，`rea` 14 s / 93 MB。排序本身不是瓶颈，**扫描与匹配**才是。

### 1.3 现行模型的性质

- **档位是无穷权重**：`high + 弱匹配` 永远压过 `normal + 强匹配`，因为档位在质量之前。这等价于把交换率设成 0（一个优先级步长值无穷大）。用户新给的顺序（档 2 在档 3 之前）要求的交换率是一个有限正数。
- **类型也是无穷权重**：同一档内，类型先于质量，所以弱匹配的应用可以压过强匹配的文件。这是用户显式要的，但代价要说清。
- **历史只做 tie-break**：band 在质量之后，所以“打开过 5 次”几乎不影响名次；设置页文案却写“历史记录和收藏夹始终排最前”。两者不一致（见 `search-ranking.md` 的 F3 与待办）。
- **三层不可比**：档位、类型、质量各自有自己的单位，字典序把它们拼起来，等于给每层赋 ∞；任何“差不多就打平”的情形都不存在，边界完全由代码顺序决定。这让参数无法校准，也让“为什么这条在前面”只能靠读代码回答。

## 2. 用户目标的精确形式

用户给的 6 条，加上第二轮确认（m02045）的置顶，按最终优先级从高到低：

| 档 | 条件 | 组内顺序 |
| --- | --- | --- |
| 0 | 历史 ≥5 次（等效） | 等效次数降序，再按质量 |
| 1 | 收藏（名字命中） | 质量 |
| 2 | 高优先 + 强匹配 | 显示优先级 → 质量 |
| 3 | 正常 + 强匹配 | 显示优先级 → 质量 |
| 4 | 高优先 + 弱匹配 | 显示优先级 → 质量 |
| 5 | 正常 + 弱匹配 | 显示优先级 → 质量 |
| 6 | 低优先 | 质量 → 显示优先级 |

把它写成比较键：

```text
Gate 0  历史 ≥5（等效次数）                  → E 降序 → 六质量键
Gate 1  收藏且名字命中                       → 六质量键
Gate 2  Score 降序（26 / 22 / 18 / 16 / 8）   → TypeRank → 六质量键
Gate 3  低优先（未进 Gate 0/1，且不满足 E ≥ 3）  → 六质量键 → TypeRank
```

三条容易忽略的推论：

- 强/弱与档位做交换的那四档，只要求“强/弱”这一层参与跨档比较，**不要求**质量连续值参与。所以 `C` 是二值，`P` 是三值，分值只需要 4 个不同的数。
- 历史 3–4 次要插在“高 + 强”与“正常 + 强”之间，这用字典序表达不了，必须有一个标量；分值是必要的，不只是好看。
- 门不能用分值代替：如果 H5 写成 34 分，未来任何新增加分项都可能超过它，而“置顶”的语义是不允许被超过。门是语义，分数只是度量。

## 3. 门与分

### 3.1 定义

先比门，门内再比键：

| 门 | 条件 | 门内键 |
| --- | --- | --- |
| 0 | `E ≥ 5`（历史等效次数） | `E` 降序 → 六质量键 → 名序 |
| 1 | 收藏，且 `Match.IsMatch` | 六质量键 → 名序 |
| 2 | 其余（含历史 3–4 次） | `Score` 降序 → `TypeRank` → 六质量键 |
| 3 | 低优先 | 六质量键 → `TypeRank` |

`Score` 只在门 2 里使用：

```text
C = 强匹配 ? 1 : 0
P = 高 ? 2 : 正常 ? 1 : 0
S = 10·C + 8·P          // 历史 3–4 次的行固定 22，不参与 10/8 计算
```

| 组合 | C | P | S | 门 |
| --- | --- | --- | --- | --- |
| 高 + 强 | 1 | 2 | 26 | 2 |
| 历史 3–4 次（任意档） | — | — | 22 | 2 |
| 正常 + 强 | 1 | 1 | 18 | 2 |
| 高 + 弱 | 0 | 2 | 16 | 2 |
| 正常 + 弱 | 0 | 1 | 8 | 2 |
| 低（任意匹配） | — | — | 不计 | 3 |

`10 : 8` 就是 0.8 的交换率：升一个匹配等级值 10 分，升一个优先档值 8 分。档 3 的 18 比档 4 的 16 高 2 分，正好实现“正常强匹配压过高优先弱匹配”。

常数不是随便挑的，约束是：

```text
q = 10（匹配等级的价值），p = 8（优先档的价值）
档 3 > 档 4  ⇔  q + p > 2p  ⇔  p < q
档 2 > 档 3  ⇔  q + 2p > q + p  ⇔  p > 0
```

所以 `p ∈ (0, 10)` 都满足前四档的顺序；取 8 的理由是留出 2 分余量给 22 这个历史档，并避开 `p = 5` 时“高 + 弱”与低档强匹配同为 10 的并列。

### 3.2 强匹配的判定

```text
Strong = Match.IsMatch
      && Match.Shape <= MatchRank.ShapeInsideWord   // whole word / word start / inside word
      && Match.Tier  <= MatchRank.TierFull          // 字面名 / 简拼 / 全拼；生僻读音不算
```

`Tier` 的数值序是 `Name(0) < Initials(1) < Full(2) < FullRare(3)`，所以 `Tier ≤ Full` 表示**字面名、简拼首字母、全拼都算强匹配**（m02045 确认）。生僻读音不算：它经常是误命中，且用户无法从名字上验证。

理由：

- `Shape` 表达“查询在名字里落在什么位置”，是离散结构信号；`Contiguity`、`Coverage`、`Start` 是连续信号，适合留在桶内做细分。用连续量设阈值会让短查询命中长名字时天然判弱（coverage 低），而词首命中其实很强。
- 不用 `Contiguity == 1`：多词查询（`code atlas` 命中 `code-atlas`）的 contiguity 只有 0.5（`HighlightMask.RankFromMarks` 的 `Σ run² / matched²`），会被误判成弱匹配。
- 全拼算强匹配：中文输入法下 `xingjian` → “新建”是主路径，不能因为 tier 比简拼低就掉档。
- 散点、无名字兜底、生僻读音、纯排除查询一律弱匹配。

这个判定的边界仍需要用 §6 的标注数据验证，尤其“四字母简拼”和“词内连续”两类。

### 3.3 为什么需要门

三处语义都要求“无论别的项多好，都必须在前/在后”，这不是偏好强度，而是成员资格：

- **低档门**：低档强匹配 10 分高于正常弱匹配 8 分，任何正的 `p` 都做不到“整个低档垫底”，只能加门。
- **历史 ≥5 门**：用户明确要求“置顶”。现状 `HistoryBand` 在质量之后（`Core/SearchResult.cs:104-132`），所以 5 次只做了 tie-break，**这个功能此前从未真正生效**（m02045 原话）；本次是修 bug，不是改偏好。
- **收藏门**：用户要求“收藏也置顶，但低于历史多次”。收藏在现行实现里同样位于质量之后（`App/ViewModels/Search/Mapping/SearchResultMapper.cs:204-207` 的注释明确写着“不能压过更好的文本匹配”），本次是有意反转该决定。

门只影响分段，不影响段内顺序；段内仍按上表的键。门越多，可校准的余地越小，所以只有这三道。

### 3.4 历史

先给结论：**保留 5/3 的档位，但阈值作用在衰减后的等效次数上，而不是裸 `Count`。**

```text
E(path, now) = Σ_j 0.5 ^ (days(now - t_j) / 90)     // 每次打开一个单位，90 天半衰期
E ≥ 5     → Gate 0，置顶；门内按 E 降序
3 ≤ E < 5 → 门 2，S = 22（插在 26 与 18 之间）
E < 3     → 无加成，只做桶内 tie-break
```

数据侧现状：`SearchHistoryStore.StoredEntry` 已存 `Time` 与 `Count`（`Core/SearchHistoryStore.cs:31-35`），`UsageCounts()` 返回裸次数（`:195-211`）。一个路径同一时刻只属于一个 keyword（`:77-86`），所以“查询条件化”可以做到：只有当前查询命中该 keyword 时，才把 `E` 当作加成；否则按 `min(E, 2)` 衰减，避免别的查询的常用项跑到这次查询前面。

置顶的准入条件（防止无关文件被顶到第一）：

```text
Gate 0 准入 = (Match.IsMatch 且 !IsHistoryOnly)        // 名字真的命中
            || keyword 与查询完全相等（OrdinalIgnoreCase） // 用户起的别名，明确指向该文件
```

否则该行留在门 2，按 `NoMatch` 走，维持现行 `IsHistoryOnly` 的语义。

为什么不用裸次数：打开行为受位置影响（排得越前越容易被点），裸次数会把“曾经排得前”固化成“永远排前”。这是推荐系统里的 position bias，也是桌面搜索里 frecency 类方案（Firefox Places 的 frecency = frequency × recency）要衰减的原因。ACT-R 的 base-level activation（`B_i = ln Σ t_j^-d`）给出了同一件事的记忆心理学解释：可提取性随访问频率上升、随间隔时间下降。

为什么不用 ACT-R 原式：`ln Σ t^-0.5` 的数值不可解释，没法直接说“5 次”。指数半衰期的“等效次数”能保留用户熟悉的 5/3 词汇，也能把旧数据一次性迁移：`E = min(Count, 10)` 再按最近一次 `Time` 衰减，幂等。

上限：Gate 0 最多 3 条、门 2 的 22 档最多 10 条，按 `E` 降序取。第 4 条 5 次以上的记录降到 22 档而不是掉到队尾，避免“第 4 名突然消失”。这个 3/10 是防自激的产品上限，可用日志校准。

### 3.5 收藏

- 收藏进 Gate 1，在 H5 之下、其余之上（m02045）。
- 准入：`FavoriteSearchHelper.ComputeMatch(fav, fuzzy).IsMatch` 且路径可用（现行 `SearchResultMapper.cs:200-202` 已有这两个条件），所以不匹配的收藏不会出现在结果里，更不会置顶。
- 代价：收藏行不再继承 Files 的类型位次，也不再看优先档，直接排到所有普通行前面。这是“置顶”的应有之义，但与 `SearchResultMapper.cs:204-207` 的原决定相反，必须在设置文案与更新日志里写明。
- 门内顺序：质量键 → 名序。收藏列表本身的顺序不做自定义（用户没要求，也避免第三个排序来源）。

### 3.6 与现行实现的差异（行为层面）

| 场景 | 现行 | 本方案 |
| --- | --- | --- |
| 高优先弱匹配 vs 正常强匹配 | 高优先在前 | 正常强匹配在前（16 < 18） |
| 低优先强匹配 vs 正常弱匹配 | 低优先在前（档位在质量前） | 低优先在后（硬门） |
| 低优先段的内部顺序 | 档位 → 类型 → 质量 | 质量 → 类型 |
| 历史 5 次 | 只做 tie-break（功能实际未生效） | Gate 0 置顶，按衰减后的等效次数 |
| 历史 3–4 次 | 只做 tie-break | 门 2 的 22 档（在 26 与 18 之间） |
| 收藏 | 质量之后 tie-break | Gate 1 置顶（低于 H5） |
| 类型顺序 | 桶内压过质量 | 不变（低档与置顶行除外） |

## 4. 为什么这样建模

### 4.1 这是“两特征线性排序器”，不是拍脑袋

`S = a·C + b·P` 就是一个两特征的线性打分器，特征只有“匹配等级”和“优先档”。把它写成线性形式有三个好处：

- 参数只有两个，可以用少量标注校准（§6），不需要模型服务、不需要训练管线。
- 每个参数都有单位解释（1 个匹配等级 = 10 分），测试可以钉死边界。
- 与 nDCG 这类分级相关度指标兼容：桶就是离散的相关度等级，桶内再按质量细分。

对比学习排序：LambdaMART 一类方法（Burges, MSR-TR-2010-82）需要成对标注与大量查询；本地搜索是单用户、短查询、候选集小、冷启动无标注，训练成本与可解释性都不划算。真正值得借的是它的评测方法（nDCG、成对比较），不是模型本身。

对比 BM25F：BM25F 的价值在“多字段 + 词频 + 长度归一”，文件名是极短字段、几乎没有词频信号、IDF 也不稳定（每个盘的索引不同）。它能借的只有“字段加权 + 饱和”的思想；我们已经有 `MatchRank` 的 tier/coverage，不需要再引入一套。

对比 Windows Search：`System.Search.Rank` 是 0–1000 的查询期整数相关度，越大越相关，支持按属性加权（`System.Search.Rank` 文档）。这是“整数分 + 档位”的现成先例：整数分便于解释与截断，档位便于产品控制。本文的分值就是同一形状，只是单位换成了“匹配等级”。

### 4.2 硬门与软加权的分工

IR 与搜索产品里有两个极端：

- **硬门（pinned / elevation）**：满足条件的文档直接排到前面，不看相关性。Elasticsearch 的 `pinned` 查询、Solr 的 query elevation 都是这个语义。优点是可控、可解释；缺点是错一条就顶掉一条更好的结果。
- **软加权（boost）**：加一个分值，相关度仍能翻盘。优点是稳健；缺点是用户“设了高档却看不到”的抱怨会回来。

本方案的分工：

- 档位与匹配之间用**软加权**（8 分），因为用户明确要求“正常强匹配压过高优先弱匹配”。
- 低档、历史 ≥5、收藏用**硬门**，因为它们表达的是“永远最后/永远最前”，不是偏好强度。
- 类型顺序是**桶内硬约束**（不是分值），因为它是用户显式排的顺序，语义就是“同一档里先看这一类”。

这也解释了为什么不能只用一个加权和：低档强匹配（10）必须排在正常弱匹配（8）之后，任何正的 `p` 都做不到，只能加门。门是必要的，但门越少越好——本方案只有三道（H5、收藏、低档）。

### 4.3 交换率 0.8 的含义与风险

0.8 是**边际替代率**：用户愿意用 0.8 个优先档换 1 个匹配等级。它决定了“优先级能翻多大的质量差距”：

- 交换率越大（p 越接近 10），高优先的弱匹配越容易压过正常强匹配（p ≥ 10 时完全压过，回到现状）。
- 交换率越小，优先级越接近只做 tie-break（p → 0）。

0.8 是产品判断，不是数据结论。必须做两件事：写进设置文案（“高档能把弱匹配提到正常强匹配附近，但不能压过它”），并用 §6 的日志校准。可接受的搜索范围是 `p ∈ {6,7,8,9}`；`p = 8` 是当前先验。

### 4.4 类型顺序的代价

桶内“类型先于质量”意味着：同一档内，一个弱匹配的应用会压过一个强匹配的文件。这是用户要的（显示优先级是显式偏好），但它与“相关性优先”的常识冲突。两个缓解：

- 设置页文案写明“结果类型顺序在同一档位内优先于匹配度”。
- 评测时单独看“类型顺序导致的 nDCG 损失”，如果损失很大，再把类型降级为“同质量档内 tie-break”（那是另一个产品决定，不在本方案默认值里）。

### 4.5 线性模型的理论边界

用户问的是“这种线性的思维从理论上讲有没有问题”。分四点回答。

**一、严格说它不是线性模型，而是“分层字典序 + 层内线性”。** 字典序偏好无法用任何有限权重的加性效用表示（ℝ² 上的字典序没有连续效用表示，这是 Debreu 的经典结论）。门就是字典序的残余：低档永远最后、5 次永远置顶、收藏永远在普通行之前。把它们写成分数只是看起来统一，实际会被任意大的新加分项推翻。所以门留在分数外面，不是实现偷懒，而是语义要求。

**二、层内线性在这里没有外推风险。** 特征只有 `C∈{0,1}`、`P∈{0,1,2}` 六个格子，任何满足 6 档顺序的赋值都等价于一张查表；线性形式不会在没见过的区域“猜”出别的顺序。真正被假设的是**边际替代率恒定**：0.8 在所有查询、所有目录、所有时段都一样。这个假设可以被数据推翻（§6），但不会被“线性”本身推翻。

**三、10 和 8 是序数，不是可加的区间量。** 把它们相加，等于宣布“一个匹配等级 = 0.8 个优先档”这一交换处处成立。用于排序是合法的（表示定理保证存在一个与偏好一致的序），但不能把“26 比 18 高 8 分”解释成概率差。若要解释，做 logistic 校准：

```text
P(打开) = σ(α·C + β·P + γ·历史项)      β/α 就是经验交换率
```

同一个排序仍然成立，只是分数从“点数”变成 log-odds。这一步不需要模型服务，只需 §6 的日志。

**四、二值化不是偷懒，是偏好本身逼出来的。** 假设质量 `q ∈ [0,1]` 连续、还想保住“正常强 > 高弱”：

```text
10·q_s + 8 > 10·q_w + 16   ⇒   q_s − q_w > 0.8
```

也就是说，切分两侧合计只剩 0.2 的质量余量。质量必须近似二值，边界处必然有跳变：`q` 从 0.79 变到 0.81 可能跨过 10 分的档。这不是实现缺陷，是 0.8 交换率的算术后果。缓解办法只有一个：桶内保留连续质量键（已经是这样），不要再把 `C` 换成 `q` 去追求“平滑”——那会直接违反 6 档顺序。

还有三条容易忽略的推论：

- **无交互假设**：加性意味着“优先档对价值的边际影响恒定”。如果以后想按目录或查询长度调交换率，那是交互项，超出本模型，需要分层模型（例如按查询长度分组的系数）。
- **IIA**：加性分数下，两条结果的相对顺序不随候选集变化。这带来稳定，但也排除多样性/配额（例如“同一目录最多 3 条”）；要做只能在分数之外加约束。
- **质量用了两次**：`C` 是质量键的粗化，桶内又用同一批键细排，所以质量对效用的影响是阶跃而非线性；不要以为“coverage 再高一点就值 10 分”。

结论：理论风险不在“用了线性”，而在“把 0.8 当常数且不校准”，以及门的边界是否真的符合偏好。前者用 §6 的离线 nDCG + 在线交错解决；后者只能靠标注与复现用例。换更复杂的模型（学习排序、神经网络）不会自动解决这两个问题，只会让它们更难看出。

## 5. 架构：把分值放进截断键

### 5.1 目标形状

```text
NameSearch 扫描候选
  → 每个候选算 C（MatchRank 已有）与 P（档位解析器）
  → Score → 编进 FzfTopN 的排序键
  → 截断按 (Score, 质量键, 引擎 tie) 选
  → SearchResult 带上 Score 与质量键
  → App 再做三道门（H5 / 收藏 / 低档）与段内细分（类型、历史、名序）
```

这样截断与最终排序用同一个分数，不会再出现“App 觉得该靠前、引擎已经把它扔掉”。

### 5.2 落点

- `SearchResultRelevance.Apply(SearchResult, FzfPattern)` 已经同时拿到 `result.Path`、`result.Name`、`result.IsDir`，是算 `P` 的天然位置（`Core/IndexV2/Search/SearchResultRelevance.cs:25-42`）。
- 但截断发生在 `Apply` 之前：`NameSearch` 在 `:293`、`:315` 把候选 `topN.Add(...)`，此时只有引擎自己的 `m.SortKey`；`Apply` 只在 `:78`、`:106` 发射与 `RefineRanks`（`:148-184`）里跑。所以必须在 `topN.Add` 处就拿到 `bucket`，否则高档弱匹配仍会被质量键挤掉。
- 档位解析器只能由 App 提供（服务进程读不到用户设置），所以它要作为参数从 `SearchService` 传到 `NameSearch`，作用域仅限本地盘。网络盘保持现状（App 侧排序），并在文档里写明这个限制。

### 5.3 键的打包

`FzfTopN` 现在是 `ulong SortKey`（`Core/SearchIndex/Fzf/FzfTopN.cs:26,60-80`），三十二位质量键 + 三十二位引擎 tie 已经占满。三种改法：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A（推荐） | `SortKey = Score(6) | HighKey(32) | 引擎 tie(26)`，砍掉 tie 的低 6 位 | 改一处打包；tie 的低 6 位几乎不影响名次 |
| B | `FzfTopN` 的 entry 增加 `byte Bucket`，按 `(Bucket, SortKey)` 比较 | 改 `FzfRank`、`DrainInto`、`FzfRankRadixSorter`，面更大 |
| C | 只保留质量键，App 侧再按 Score 重排 | 不解决截断，等于没做 |

A 的风险最小：`Score` 只有 0–26（置顶与低档不进分数），6 位绰绰有余；`HighKey` 的位布局不动（`search-ranking.md` 的 F1 教训：动布局必须补 63 vs 64 的用例）；引擎 tie 的低位只影响同分同质量时的先后，而那种并列本来就由 `EntryIndex` 兜底。

### 5.4 截断的复杂度

`FzfTopN` 是“缓冲 + 定期三分区 quickselect”，摊还 O(1)/条。把 `Score` 编进键不需要改算法，只是键的构造变了一点。真正省下来的是**扫描量**：

- 去掉“有高档规则就抬到 1000”的抬升：每盘 160000 → 8160（-95%）。
- 去掉每个高档根的补搜：每次查询少 N 条完整管线，每条 8000 次扫描。
- 代价：每个候选多一次档位解析。

档位解析的成本必须实测，设计上按三层控制：

1. 路径规则：按目录缓存（`ConcurrentDictionary<string, byte>`，键是父目录）；同一目录的候选只算一次。
2. 通配符/正则：只对缓存未命中的目录求值；先用“必要字面量”预筛（`GlobMatcher` 已有 `LongestRequiredLiteral`），不命中直接返回正常。
3. 缓存上限：例如 20 万条后整体清空，避免长会话内存无界。

预算：候选 8160、目录去重后通常 < 2000，按 100–200 ns/次估算，档位解析在 1 ms 量级；若实测超过 3 ms，退回 §5.5 的降级路径。

### 5.5 降级路径

如果档位解析在真实索引上超预算，保留两层结构：

- 引擎截断只做质量键（现状），但**保留**高档根补搜；
- App 侧按 §3 的分值重排。

这样行为仍符合用户的 6 档（因为补搜保证了高档候选到达 App），代价是低档仍可能在截断时被丢掉，以及补搜的额外管线。降级路径必须在方案实施前就写好开关，避免“性能不达标再回滚代码”。

### 5.6 完整窗口

完整窗口没有 App 侧上限，`fileLimit = int.MaxValue`，是另一个性能问题：它的成本在“扫描全部 + PathTermFallback 兜底”，不在排序。本方案不改变它的语义，但有两个可选项：

- 有界化：给完整窗口也设一个上限（例如 5000），超出后显示“继续加载”，把“全部”变成“前 5000 + 分页”。这是产品改动，收益是 6.5 s → 亚秒级；风险是用户失去“列全”的能力。
- 保持现状：只把 `Score` 编进键，排序更正确，但延迟不变。

本文建议先不动完整窗口的预算，把它列进 §10 的待确认项。

## 6. 校准与评测

### 6.1 标签从哪来

可用的信号只有“打开”：

- 正例：某次查询后 30 秒内被打开的路径（强正例）；打开但超过 30 秒（弱正例）。
- 负例：同一查询下展示过但没被打开的路径。它受位置偏置影响，只能当弱负例。
- 合成查询：用高优先目录里的文件名反查（`Readme.txt` → `readme`），正例就是该文件；这类查询没有位置偏置，适合测“高档召回”。

先做 §9 的 P0：记录 `queryHash / pathHash / rank / score / bucket / opened`，不存明文。没有这份日志，任何参数都只能靠猜。

### 6.2 指标

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| nDCG@10 | `DCG = Σ (2^rel - 1) / log2(i+1)`，rel 用 3/2/1/0 | 主指标；对“置顶放错”惩罚最重 |
| MRR | 打开项排名的倒数 | 单目标查询的直观指标 |
| Pinning recall@10 | 高优先目录里的文件在同名查询下进入前 10 的比例 | 直接测“设了高档能不能看到” |
| 类型损失 | 把类型层关掉后的 nDCG 差 | 量化 §4.4 的代价 |
| p95 延迟 | 按键到首屏、引擎扫描耗时 | 性能门 |

nDCG 的 gain 用 `2^rel - 1`，是因为它对第 1 名的错误最敏感：把一条无关结果置顶，损失比把它放在第 5 名大得多。这正是“5 次置顶”这类硬规则的风险所在。

### 6.3 离线评测

- 黄金集：100 条查询 = 40 条来自历史 keyword、30 条合成文件名、30 条手写（项目名、中文、拼音、多词）。每条标注期望前 10（人工过一遍，至少标出“必须在前 3”的路径）。
- 回放：用 `Cli --search <q> --limit N --json` 抓候选与排序，离线重算指标；同一批候选上比较不同参数，避免索引变化干扰。
- 显著性：按查询做配对 bootstrap（10k 次重采样），报告 95% 置信区间；区间跨 0 就不算改进。不要用“平均分高了 0.02”下结论。

### 6.4 在线评测

单用户、低流量，A/B 不现实；用 **team-draft interleaving**：把两个排序器的结果交错成一份列表，记录用户点了谁的结果，按贡献计数。跑两周、累计 ≥30 次打开再判断。交错对位置偏置不敏感，比直接比点击率可靠。

护栏指标：零结果率、`N more` 点击率、搜完不打开的会话比例、p95 延迟。任何一项恶化超过 10%，先停。

### 6.5 参数搜索

参数只有四个，网格搜索即可：

```text
p ∈ {6,7,8,9}
H5 阈值 ∈ {4,5,6}            // 等效次数，门的位置
H3 分 ∈ {19..25}             // 3–4 次的固定档
Strong 判定 ∈ {Shape≤InsideWord, Shape≤WordStart, + Coverage≥0.5}
```

在 70 条训练查询上取 nDCG@10 最大，30 条留出验证；报告每个参数附近的平台（参数在 ±1 内指标不掉才算稳）。这不是机器学习，是把先验放在数据上检验。

## 8. 风险与边界

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 档位解析超预算 | 每次按键多几毫秒 | §5.4 的三层缓存与预筛；超 3 ms 走 §5.5 降级 |
| 高档规则覆盖过宽（例如整个盘） | 一切都置顶，等于没有优先级 | 规则保存时提示“覆盖 N 个索引文件”；可选上限（例如置顶段不超过显示名额的 1/3） |
| 低档完全不可见 | 用户找不到低档文件 | 完整窗口仍列出；设置文案写明“低档在快速窗口可能被 50 条上限挡住” |
| 历史自激 | 越点越前，新文件无曝光 | 90 天半衰期 + 3/10 条上限 + 查询条件化 |
| 类型顺序压过质量 | 弱匹配应用压过强匹配文件 | 文案写明；评测单独量化；必要时降级为 tie-break |
| 5 次置顶放错 | nDCG 断崖 | 准入只认名字命中或完全相等的 keyword；等效次数 + 最多 3 条；日志监控 |
| 收藏置顶过多 | 常用收藏挤掉更好的匹配 | 只对名字命中的收藏生效；门内仍按质量；评测看 pin precision |
| 完整窗口 6.5 s | 打开完整窗口像卡死 | 本方案不改语义；P4 再决定是否分页 |
| 两份方案并存漂移 | 实施时各取一半 | §12 的差异表；动手前合并成一份，另一份标“已合并” |

## 9. 不做什么

- 不做神经网络排序、不做云端个性化、不引入模型服务。
- 不改索引格式、不为排序重建索引。
- 不做“每条规则一个权重”的滑块：参数一多就无法解释，也无法校准。
- 不把类型顺序做成可配置的分值：它是序，不是权重。
- 不在第一阶段动内联窗口：它有自己的目录邻近度分组（`InlineListSearchHelper`），等主窗口稳定后再接。

## 12. 与 `search-ranking-redesign.md` 的差异

两份方案独立写成，结论有重叠（都用了 0.8 交换率、都把低档做成硬门、都要求历史衰减），差异在优先级与范围：

| 维度 | 本文 | `search-ranking-redesign.md` |
| --- | --- | --- |
| 截断 | P3 把分值编进引擎键，删掉 1000 抬升与补搜 | 第一阶段保留引擎截断与补搜，有界堆放第二阶段 |
| AlwaysTop | 不做；只有低档、H5、收藏三道门 | 作为一等字段（`IndexRuleSetting.AlwaysTop`）与补搜的一部分 |
| 收藏 | 进 Gate 1 置顶（低于 H5） | 只做 tie-break |
| 历史 | 读取时按半衰期算等效次数，不改存储格式 | 新增 `StoredEntry.Score` 字段并迁移 |
| 参数来源 | 先验 + §6 的离线/在线校准 | 先验 + 日志观察，校准列为第三阶段 |
| 评测 | nDCG@10、MRR、交错实验、配对 bootstrap | 以测试与基准为主，未展开统计方法 |
| 适用范围 | 排序内核与截断；完整窗口预算留待确认 | 双窗 + 内联窗口的第二阶段计划 |

合并时的建议：以本文的“分值 + 引擎键 + 校准”为骨架，把草稿的 `AlwaysTop` 与历史字段设计并入；先做 P0–P2，再决定 P3 是否随第一阶段一起上。
