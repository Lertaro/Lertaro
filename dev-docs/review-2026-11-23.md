**#560：默认索引降权先于名称质量，已复现**

报告者确认使用默认设置，补充截图的类型顺序为“文件、文件夹、应用、系统设置”。这项配置不能解释异常顺序。

原因在 [IndexRuleDefaults.cs](../Core/Settings/IndexRuleDefaults.cs) 的默认 Low 规则，以及 [RankPolicy.cs](../Core/SearchIndex/RankPolicy.cs) 先比较 Section 的顺序。新设置也会通过 `IndexRuleMigration.Ensure` 获得这些规则。

| 截图中的结果 | 命中默认规则 | 分区 |
|---|---|---|
| D 盘 Maven 下的四个目录 | 无目录降权 | Normal / Boosted |
| Program Files 下的 Marvis.7z、Marvis.exe | `%ProgramW6432%` | Low |
| 用户 AppData 下的 Marvis.log | `%USERPROFILE%\AppData` | Low |
| Windows\Temp 下的 Marvis 目录 | `%SystemRoot%` | Low |

排序先比较 `Pinned → Boosted → Low → HistoryTail`，再比较证据等级、优先级、可用历史和名称质量。因此，Normal 的分散匹配会排在 Low 的精确匹配之前。这不是 C/D 盘号排序造成的；盘号只是末尾的平局判定项。

四个目录的名称本身都包含按顺序出现的 `m-a-r-v-i-s`，是分散子序列匹配。单词查询 `marvis` 不走要求至少两个词的 `PathTermFallback`；无需用父路径里的 `maven` 解释召回。

在 5.13.6 正式便携包的 `Lertaro.Core.dll`（程序集版本 3.5.4）中运行同组名称：全部使用 Normal 时，Marvis 文件在前；加上真实默认索引规则后，顺序变成 `maven-scm-provider-cvs-commons → maven-scm-provider-git-commons → maven-scm-provider-svn-commons → smallrye-health-provided-checks → Marvis.7z → Marvis.exe → Marvis.log → Marvis`，复现截图。

“精确优先、左侧优先”在同一分区内仍然成立。质量内部先比较连续性和单词形态，再比较左侧位置、类型顺序及覆盖率；显式置顶和目录降权有更高优先级。若希望这些路径立即恢复正常名称排序，可在索引规则中移除对应 Low 规则。若希望默认情况下也做到“精确名称跨越目录降权”，需要调整分区与证据等级的相对顺序；本次保留现有排序策略并提交复现测试。

**#567：确认模拟输入过滤引入的兼容性变化**

5.13.5 到 5.13.6 之间，相关行为变化来自 `0c4142e9`。之前只在内嵌搜索输入转发处过滤注入事件；之后 [KeyboardHookService.cs](../Core/Hook/InlineSearch/KeyboardHookService.cs) 在整个回调入口遇到 `LLKHF_INJECTED` 就返回，包括 key-down、key-up、双 Ctrl、Ctrl+G 和其他全局快捷键。

这会拒绝经软件重新注入的真实用户操作，例如通过键位映射或输入转发工具发出的 Ctrl/G。受影响的依据是事件标志，不能仅凭键盘品牌或有线/无线连接判断。Ctrl 是物理事件而 G 是注入事件时，G 也会在检测前返回；混合来源的按下/释放还可能使双击检测器收不到释放事件。

完整回调对照测试中，物理双 Ctrl 触发一次，带 `0x10` 注入标志的同样序列触发零次；原有 AHK 防误触测试保持通过。快捷键相关 28 项测试通过。这确认了该提交能够造成报告中的退化，但 issue 尚无按键来源或事件 flags 记录，不能把报告者的具体环境认定为已经确认。

定位报告者环境时，首先确认是否运行键位映射、宏、远控或输入转发软件，并记录 Ctrl 与 G 的 `vkCode / scanCode / flags`。如果 flags 带 `0x10`，就命中了这条早退；如果均为物理事件，则应继续查 Hook 是否安装成功、是否被系统超时移除、全屏/进程门控，以及 Ctrl+G 所需的文件对话框和最近浏览路径状态。直接删除注入过滤会重新引入 #555 的模拟 Ctrl 误触；兼容软件映射需要明确的允许策略。

**LocalSend：协议版本一致，已修复发现的问题，仍有性能与功能差距**

上游 1.19.0 的应用常量仍声明 **2.2**，本地 `LocalSendDeviceInfo.Version` 也为 **2.2**。本地的 v2 info/register、prepare-upload、upload、cancel、IPv4/IPv6 发现、TLS 指纹、PIN、SHA-256 和时间戳主要字段与所核对的上游一致。代码中出现 v3 模块不能据此把正式客户端协议认定为 v3。

本地额外保留 v1 路由。`download=false` 与未实现 prepare-download/download 相符；网页链接分享是可选能力，需要额外实现，不能把已有推送收发当作已支持链接分享。

本次完成的修复：

1. **连接上限前移**：接受 socket 后立即取得名额，超额立即关闭，避免先创建任务、让无限量已接受 socket 等待 5 秒；保持 16 个活动连接上限。
2. **发送取消传递到流**：实现 HttpContent 的 CancellationToken 重载，使源读取和网络写入都可取消；发送缓冲使用 ArrayPool，避免每个文件重新分配 1 MiB 数组。
3. **完成上传后解除停滞计时器**：原代码仅“不再重置”30 秒计时器，仍会在接收端校验期间触发；现改为禁用该计时器，用户取消仍有效。取消请求的 HTTP response 也及时释放。
4. **16 KiB 文本预览限制**：按 UTF-8 字节和声明大小限制；大文本省略预览、走完整文件传输。旧客户端带超大预览的消息仍要求同意，随后返回上传 token，而非直接 204 丢弃正文。
5. **发送选择完整性**：缺失或不可枚举的选择返回错误，不再静默跳过后只发送剩余文件；目录枚举支持取消并避免额外 GetFiles 数组。
6. **重名耗尽保护**：1000 次后缀尝试耗尽后拒绝接收，避免将未保留、可能已存在的第 1001 个名字交给 FileMode.Create。
